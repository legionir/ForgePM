# قوانین رفتار ایجنت با Execution Ledger

این فایل دستور کار است، نه توضیح اختیاری. Ledger و Gate منبع حقیقتِ وضعیت کارند؛ گفت‌وگو، حافظهٔ ایجنت و فایل محلی جای آن‌ها را نمی‌گیرند.

## چرا

هر تصمیم، مدرک، فرض و مانع باید هنگام رخ‌دادن ثبت شود تا نشست تازه بتواند از وضعیت واقعی ادامه دهد. چیزی که ثبت نشده، برای Gate و بازبین اثبات نشده است.

## شروع و ادامه

1. در آغاز یا ادامهٔ هر نشست `session_start` را صدا بزن؛ شش بخش را به ترتیب اولویت بخوان و سپس برای جزئیات `exec_ledger_status` را اجرا کن.
2. پیش از هر نوشتن یا ادامهٔ کار، blockerها و معیارهای بی‌مدرک را بررسی کن.
3. برای کار جدید، `exec_task_start` را با معیارهای قابل‌اندازه‌گیری و `allowed_paths` مشخص صدا بزن.
4. اگر ابزار Ledger در دسترس نیست یا ماژول خاموش است، **توقف کن**؛ علت را در گزارش بگو و جایگزین نساز.

## محرک‌ها

- آغاز کار، ادامه پس از وقفه یا ابهام دربارهٔ وضعیت → `exec_ledger_status`؛ اول وضعیت موجود را بخوان.
- کار تازه با دامنه و معیارهای روشن → `exec_task_start`؛ تسک و معیارها را پیش از تغییر بساز.
- مدرک قابل‌خواندن برای یک معیار → `ledger_add_evidence`؛ فقط پس از بررسی ref ثبت کن.
- انتخاب میان گزینه‌ها یا تغییر دارای ریسک → `exec_policy_check`؛ فقط اگر سطح `deny` نبود `ledger_record_decision`؛ سطح را سیاست محاسبه می‌کند.
- فرض انسانی، ابهام یا انتخاب خارج از اختیار ایجنت → `ledger_ask_human`؛ گزینه‌ها و اثر هرکدام را بنویس.
- نقص، ریسک، تعهد، سؤال یا کارِ بعداً → `ledger_add_open_item`؛ نوع و blocking بودن را صریح کن.
- نیاز به دیدن یا بستن آیتم‌های موجود → `ledger_list_open` سپس `ledger_resolve_item`؛ blocker را نرم فقط انسان می‌بندد.
- پایان پیاده‌سازی و گزارش آنچه مانده → `exec_submit_exit_report`؛ هر فهرست خالی را صریح تأیید کن.
- درخواست بستن تسک → `exec_task_complete`؛ فقط پاسخ مثبت Gate اجازهٔ بسته‌شدن می‌دهد.
- ثبت دانشِ مشاهده‌شده با منبع واقعی → `fact_record`؛ فایل‌ها را ForgePM می‌خواند و hash می‌کند. حدس فقط `kind:'assumption'` است؛ `kind:'fact'` با `source:'agent_guess'` رد می‌شود.
- جست‌وجوی دانش موجود → `fact_query`؛ اگر `status:'stale'` یا هشدار برگشت، مقدار را حقیقت جاری فرض نکن.
- تغییر منبع فایل یا هشدار stale → `fact_verify`؛ تصمیم وابسته دوباره بازبینی و blocker را با evidence حل کن. بررسی خودکار در `session_start`، پیش از Gate و دوره‌ای اجرا می‌شود.
- ارتقای فرض به fact → `fact_promote` را فقط انسان با reason/evidence اجرا می‌کند؛ ایجنت هرگز خودش حدس را fact نمی‌کند.

## کِی از انسان بپرسم

اگر تصمیم سطح `approval` دارد، تغییر را اعمال نکن؛ تصمیم را ثبت و تا تأیید انسان صبر کن. اگر پاسخ یک سؤال می‌تواند دامنه، قرارداد، داده یا الزام را عوض کند، با `ledger_ask_human` بپرس. سکوت تأیید نیست و timeout وجود ندارد.

## حین کار

- پیش از اقدام بیرونیِ قابل‌توجه، `journal_start` را با اثر مورد انتظار و تکرارپذیری واقعی ثبت کن؛ پس از بررسی نتیجه، فقط یک‌بار `journal_done` یا `journal_fail` را اجرا کن.
- `session_start` هر اقدامِ نیمه‌تمام را `unknown` می‌کند. تا تعیین وضعیت آن، قفل کد اجازهٔ ابزارهای نوشتن عادی را نمی‌دهد. اقدام غیرتکرارپذیر را دوباره اجرا نکن؛ وضعیت واقعی را بررسی و journal را settle کن، یا از انسان بپرس. تکرار idempotent فقط با همان task/action/target/expected_effect و همراه با رویداد `journal.retry_started` مجاز است.
- `exec_ledger_reconcile` وضعیت فایل‌های بسته‌شده، Gate، فکت‌های stale، journalهای باز و اختلاف `changed_files` با diff اندازه‌گیری‌شده را گزارش می‌کند.

مدرک را پس از مشاهدهٔ واقعی ثبت کن، نه از روی حدس. برای هر تصمیم، گزینه‌ها، انتخاب و دلیل را ثبت کن. `rationale` نمی‌تواند سطح سیاست را پایین بیاورد. نتیجهٔ نامعلوم را «موفق» جا نزن؛ آن را به‌عنوان آیتم باز یا سؤال انسانی نگه‌دار.

## پایان

Exit Report را کامل بفرست؛ یافته‌ها و تست‌های اجرا‌نشده را حذف نکن. سپس Gate را اجرا کن و هر `blocked_by` را با ابزار نام‌برده حل کن. هیچ مسیر مستقیمی در پنل یا API برای تغییر Work Item به `done` جای Gate را نمی‌گیرد.

## ممنوع

- ممنوع: سطح ریسک را خودت تعیین یا جعل نکن؛ چون فقط جدول سیاست حق تعیین سطح دارد.
- ممنوع: تصمیم `approval` را پیش از تأیید انسان اعمال نکن؛ چون رد Gate یعنی هنوز اجازه نداری.
- ممنوع: blocker را نرم نبند، معیار را waive، الزام را drop، scope را گسترش یا حدس را fact نکن؛ چون این تغییرها انسانی و قابل‌ممیزی‌اند.
- ممنوع: وقتی ابزار Ledger در دسترس نیست ادامه نده و جایگزین نساز؛ چون مسیر جایگزین وضعیتِ ثبت‌نشده و غیرقابل‌اعتماد می‌سازد.

## شش نمونهٔ دستور CLI انسانی

```sh
npm run ledger -- list
npm run ledger -- show T-001
npm run ledger -- resolve OI-001 --status resolved --note "توضیح قابل‌ممیزی برای بستن آیتم"
npm run ledger -- answer Q-001 "پاسخ انسان"
npm run ledger -- approve D-001 --reason "تأیید و دلیل انسان"
npm run policy:print
```

این دستورها به مسیر REST انسانی وصل‌اند؛ رد، waiver و drop هم فقط از CLI/پنل انسانی مجازند. کلید ایجنت نباید `ledger:decide` داشته باشد. برای تغییر سیاست، فقط انسانِ مجاز از `npm run policy:set -- --from policy.json` استفاده می‌کند. کلید یا فایل دارای secret را commit نکن.
